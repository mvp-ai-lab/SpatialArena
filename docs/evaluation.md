# Evaluation

The benchmark evaluator is artifact-only. External methods receive canonical benchmark scene folders, produce
standardized predictions, and the evaluator reads only those prediction files plus canonical ground truth. It
does not import or instantiate DA3, VGGT, AMB3R, or any other external model.

This document covers the evaluation datasets, the benchmark root and scene layout, the evaluated methods and
input-modality tracks, the protocol and metrics of each task, the full-standard case lists, the output tree,
and the generated per-scene inventory. The SLAM track's protocol is in
[`benchmark/slam_protocol.md`](benchmark/slam_protocol.md); training datasets are in
FeedForward-Benchmark's `docs/training_data.md`.

Where the numbers come from (never hand-typed or guessed):

- Per-scene image counts: [Scene Inventory](#scene-inventory) below, generated by
  `scripts/preprocess/export_benchmark_data_doc.py` from the live `metadata.json` files under `benchmark_root`.
- Case-list scene counts: `scripts/test/full_standard_*_cases*.txt` and
  [Full-Standard Case Lists](#full-standard-case-lists).
- Evaluated images per scene: the frame-selection cap in `scripts/inference/adapter_utils.py::select_interval()`
  (see [Frame Selection](#frame-selection)) applied to the per-scene totals.
- Licenses: `spatialarena/dataset_licenses.py`'s `SOURCE_LICENSES` registry (each entry verified against the
  source's own page; see `benchmark/data_leakage_notes.md` for the companion training-data-overlap research).
- Scene type: dataset-level classification from each source's publication, cross-checked against a real sample
  image for the less-documented ones (`texturepoorsfm`, `hiroom`).

The Overview and Datasets sections are hand-maintained: after regenerating the inventory or the case lists,
re-derive their counts rather than trusting them blindly.

## Overview

### Tracks x Tasks

| Task | Valid tracks |
|---|---|
| MonoDepth | `rgb`, `rgb_masked_depth` |
| VideoDepth | `rgb`, `rgb_cameras` (SpatialArena only: the one dataset whose released GT has camera poses), `rgb_masked_depth`, `rgb_sparse_depth` (KITTI) |
| MVRecon | `rgb`, `rgb_cameras`, `rgb_depth`, `rgb_masked_depth`, `rgb_masked_depth_cameras`, `rgb_sparse_depth`, `rgb_sparse_depth_cameras` |
| SfM | `rgb`, `rgb_depth`, `rgb_masked_depth`, `rgb_masked_depth_cameras`, `rgb_sparse_depth`, `rgb_sparse_depth_cameras` |
| SLAM | `rgb`, `rgb_depth`, `rgb_masked_depth` |

(`spatialarena/task_track_matrix.py` is the source of truth; a
(task, track) pair only runs if it's in this table **and** the selected
method's own `tracks` tuple.)

`rgb_masked_depth` hands the method the GT depth priors with part of every
map dropped, and `rgb_masked_depth_cameras` those plus the GT camera poses
(`spatialarena/depth_prior_masking.py`, default protocol
`cells32-drop0.5-v1`): each depth map, at its own resolution, is cut into
square cells, 32 along its longer side, and a fixed fraction of the cells
(0.5 by default; the cell order is seeded by the scene name and the image's
path in the scene, so every run and every method gets the same mask, and the
masks of one image are nested across ratios) is set to invalid. The ratio and
grid can be set per run with `BENCHMARK_DEPTH_MASK_RATIO` (in [0, 1)) and
`BENCHMARK_DEPTH_MASK_GRID` in a model entry's `env`; a non-default setting
runs under its own method ID (`PI3_X-mask0.7_rgb_masked_depth`) and
prediction cache key; already-invalid pixels stay invalid, so sparse GT
(DTU, ETH3D, KITTI) becomes sparser still. Scoring is unchanged: every
GT-valid pixel, dropped or kept, after the task's usual alignment. These
tracks run on every dataset with depth priors (cases without them are skipped
as `skipped_missing_depths`); on SfM, `rgb_masked_depth_cameras` measures how
faithfully the given poses come back out, not pose estimation. PI3_X,
MAPANYTHING and OMNIVGGT take these tracks.

`rgb_sparse_depth` gives the method the sparse depth a real system has, and
`rgb_sparse_depth_cameras` that plus the GT cameras
(`spatialarena/sparse_depth.py`, priors built by
`scripts/preprocess/materialize_sparse_depth_priors.py` into
`<benchmark_root>/_sparse_depth/`): on VideoDepth KITTI, each frame's raw
Velodyne scan projected into the left colour camera with KITTI's calibration
(about 4-5% of the pixels, against the accumulated GT's ~20%); on MVRecon DTU,
ETH3D and Tanks and Temples, and on SfM those plus IMC and TexturePoorSfM, each image's observed COLMAP keypoints at the depth of their 3D
point (typically 0.1-1% of the pixels). Datasets without such a source (no
LiDAR, or a COLMAP model without 3D points) do not run these tracks. The SfM
points come from the reconstruction the SfM poses are scored against, so SfM
results on these tracks are SfM-assisted, not pose estimation. The points are
stored as lists and drawn for each method as small squares sized so that every
point survives the method's own nearest-neighbour resize as about one pixel.
Scoring is unchanged. PI3_X, MAPANYTHING and OMNIVGGT take these tracks.

## Datasets

### MonoDepth / marigold

One registry entry that bundles four independently-sourced monocular test
splits, repackaged for convenience by the Marigold authors
(`share.phys.ethz.ch/~pf/bingkedata/marigold/evaluation_dataset/`). Each
sub-scene is evaluated as its own "scene" in our pipeline.

| Sub-scene | Images | Evaluated | Original source | Scene type | License |
|---|---:|---:|---|---|---|
| nyuv2 | 654 | 654 | NYU Depth V2 (Silberman et al., ECCV 2012) | indoor, static, real | unconfirmed (no published license found; citation requested) |
| kitti | 652 | 652 | KITTI (Eigen split) | outdoor, dynamic (driving), real | restricted_noncommercial (CC BY-NC-SA 3.0) |
| eth3d | 454 | 454 | ETH3D | indoor+outdoor, static, real | restricted_noncommercial (CC BY-NC-SA 4.0) |
| diode | 771 | 771 | DIODE | indoor+outdoor, static, real | permissive (MIT) |

Track: `rgb` only (MonoDepth has no meaningful `rgb_depth`/`rgb_cameras`
conditioning axis -- predicting depth when depth is already given as a
prior isn't a useful benchmark).

### MonoDepth extension datasets: aerialmetric, hammer, ibims1, spring, synth4k

Five more MonoDepth datasets. HAMMER, iBims-1, Spring and Synth4K follow
MoGe-3's zero-shot suite; AerialMetric adds aerial (UAV) viewpoints. They use
the same protocol as `marigold`
(by default the per-image GT-only Huber IRLS fit in the method's native output space, the same depth metrics) and, like every
MonoDepth case, are evaluated on every image of a scene (no frame cap; see
Frame Selection). Every scene uses the canonical MonoDepth layout:
`images/`, `depths/` (float32 `.npy` metres, `0` = invalid), optional `masks/`
(255 = evaluate), `materialized_full.json` (per-frame records with pixel
intrinsics and the source sample id), and the scene's depth limits in
`metadata.json` (`min_depth`, `max_depth`, `depth_scale`, read by
`resolve_depth_config`). Frame lists are committed under
`spatialarena/eval/monodepth_splits/<dataset>/<scene>.txt`.

| Dataset / scene(s) | Images | Evaluated | Source | GT range (m) | Scene type | License |
|---|---:|---:|---|---|---|---|
| hammer / hammer | 775 | 775 | MoGe's processed HAMMER (HF `Ruicheng/monocular-geometry-evaluation`) | > 1e-3 | indoor tabletop, real | permissive (MIT) |
| ibims1 / ibims1 | 100 | 100 | MoGe's processed iBims-1 | > 1e-3 | indoor, real | permissive (CC BY 4.0) |
| spring / spring | 1,000 | 1,000 | MoGe's processed Spring (every 5th train frame) | > 1e-6 (not metric) | synthetic film, dynamic | permissive (CC BY 4.0) |
| synth4k / cyberpunk, deadisland, spiderman2, spidermanmm, watchdoglegion | 1,960 (412 / 362 / 412 / 362 / 412) | 1,960 | InfiniDepth's Synth4K (HF `ritianyu/game_4k_data`), 3840x2160 | (3, 150) | game-captured, synthetic | unconfirmed (game imagery; packaged on our HF repo with attribution) |
| aerialmetric / decoupled, oblique, wild | 3,596 (2,313 / 698 / 585) | 3,596 | AerialMetric Test-Split (HF `Kuiee/AerialMetric-ECCV2026`) | (1e-3, 400) | aerial (UAV), real | mixed: Decoupled/Oblique academic-only, Wild unconfirmed (YouTube frames) |

Per-dataset preparation (all GT in metres unless noted):

- `hammer`, `ibims1`, `spring` (`scripts/download/moge_eval.sh`,
  `scripts/preprocess/materialize_moge_eval.py`): MoGe's exact frames;
  MoGe's log-encoded `depth.png` is decoded and MoGe's own validity is baked
  in (unknown/infinite depth and depth beyond 1000x the frame's 1% depth
  quantile -> 0); `meta.json` UV-normalized intrinsics are scaled to pixels.
- `synth4k` (`scripts/download/synth4k.sh`,
  `scripts/preprocess/materialize_synth4k.py`): InfiniDepth publishes no
  evaluation frame list, so each game keeps half of its scorable frames
  (`--frame_fraction 0.5`; a frame is scorable if it has GT inside (3, 150) m),
  uniformly spaced over its sorted frames: 1,960 of the 3,950 complete frames
  (412 / 362 / 412 / 362 / 412). `--frames_per_scene 100` restores the old
  100-frame selection. RGBA PNGs are stored as RGB PNG; EXR depth as `.npy`; the
  high-frequency masks are kept under `highfreq_masks/` for the phase-2
  fine-detail metrics. No intrinsics (InfiniDepth evaluates without them), so
  the geometry metrics are not computed.
- `aerialmetric` (`scripts/download/aerialmetric.sh`,
  `scripts/preprocess/materialize_aerialmetric.py`): Test-Split only, three
  scenes, each keeping half (`--frame_fraction 0.5`, the default) of its
  frames with GT inside (1e-3, 400) m, uniformly spaced over the sorted
  sample ids. `decoupled` = 2,313 frames, half of each of the 4 sites
  (pitch/altitude/FOV sweeps, 4,625 frames available), `oblique` = 698 of the
  1,397 `val_index.txt` samples, `wild` = 585 of the 1,184 frames of 100
  online UAV videos (low-resolution 504x280 GT, per-frame COLMAP intrinsics;
  two Wild videos lie entirely beyond 400 m and are never kept). The
  dynamic-object masks are applied. Releases before 2026-10-20 used 100
  frames per scene (`--frames_per_scene 100`).

`spring` is excluded from the aggregate ranking because several evaluated
methods train on the Spring train split (see
`docs/benchmark/data_leakage_notes.md`).

### VideoDepth / sintel

MPI-Sintel's depth extension (Butler et al., ECCV 2012 + Wulff et al.
depth data). 23 short animated-film clips. **Scene type:** outdoor and
indoor settings from the open-source film "Sintel," dynamic (characters,
camera motion, some cloth/water simulation), fully synthetic (rendered,
not captured). **License:** unconfirmed -- no formal license/terms-of-use
document was found on the official site (`sintel.is.tue.mpg.de`) during
this research pass; verify directly with MPI before any redistribution
beyond evaluation use.

### VideoDepth / bonn

Bonn RGB-D Dynamic Dataset (Palazzolo et al., IROS 2019). 26 sequences,
110 frames each (2,860 total, 2,600 evaluated after the 100-frame cap).
**Scene type:** indoor, dynamic (people manipulating boxes/balloons in
front of a static camera), real (Kinect RGB-D capture). **License:**
restricted_noncommercial -- CC BY-NC-SA 3.0.

### VideoDepth / kitti

Real KITTI raw driving sequences (distinct sequences from the
`marigold/kitti` MonoDepth sub-scene above, though both ultimately derive
from the same KITTI release). 13 sequences. **Scene type:** outdoor,
dynamic (moving vehicle, other traffic/pedestrians), real (driving
platform with stereo cameras + LiDAR). **License:** restricted_noncommercial
-- CC BY-NC-SA 3.0.

### VideoDepth / dycheck

DyCheck iPhone captures (Gao et al., NeurIPS 2022) as distributed for MegaSaM's evaluation: 12 scenes, camera 0
only (180-475 frames each, 3,952 total, 1,200 evaluated after the 100-frame cap). RGB is 720x960 (`haru-sit`
960x720) and GT depth half that; GT depth is metric (0.2-3 m). **Scene type:** people, pets and objects in motion
in front of a handheld phone, indoor and outdoor, real. `rgb_cameras` priors come from the per-frame DyCheck
cameras (`dense/dycheck/camera/`, converted by `materialize_benchmark_camera_priors.py`). **License:**
Apache 2.0 (the DyCheck README: "Both our code and dataset are released under the Apache 2.0 license"); MegaSaM
licenses its non-software materials CC BY 4.0. Both allow redistribution with attribution; cite DyCheck and MegaSaM.

### SpatialArena (all five tasks)

Our own captures with a handheld 3-camera LiDAR rig (`docs/benchmark/spatialarena.md`): 30 indoor and outdoor scenes
with refined, Sim(3)-aligned metric poses, LiDAR depth and GGGS dense depth. MonoDepth: 19 scenes, 1,688 images (a
time-spread 10% of each scene above its median GGGS render PSNR, minus 203 frames dropped by manual review); VideoDepth:
15 single-camera clips of 7 scenes (4,510 frames, 26 of them without GT after review, `gt_excluded`); MVRecon: 6
scenes with every image (5,295) and the LiDAR map cropped to what they see as GT geometry; SfM: 7 scenes, all 3 cameras (7,680 images);
SLAM: 8 single-camera 5 Hz sequences, each in one range track (3 short, 2 long, 3 large). People and vehicles are
blacked out of the depth tracks' images. **License:** CC BY-NC 4.0. Downloaded from the release by
`scripts/download/spatialarena.py`; `SPATIALARENA_ROOT` reads it from a materializer output root instead.

### SfM+MVRecon / eth3d

ETH3D high-resolution multi-view benchmark (Schöps et al., CVPR 2017). 13
scenes shared identically between the `SfM` and `MVRecon` tasks (`SfM/
eth3d` is a filesystem symlink to `MVRecon/eth3d` -- same bytes, not a
separate copy). **Scene type:** mixed indoor (`delivery_area`, `electro`,
`office`, `pipes`) and outdoor (`courtyard`, `meadow`, `playground`,
`terrace`, `terrains`), static, real (DSLR + multi-camera rig capture).
Two scenes (`meadow`, `terrace`) have no ground-truth mesh in DA3-BENCH's
repackaging and always fail MVRecon's geometry evaluation (data gap, not
a pipeline bug -- see [Full-Standard Case Lists](#full-standard-case-lists)).
**License:** restricted_noncommercial -- CC BY-NC-SA 4.0.

### SfM+MVRecon / tanks_and_temples

Tanks and Temples (Knapitsch et al., ACM TOG 2017), downloaded via Free
View Synthesis's `ibr3d_tat.tar.gz` repackaging. 6 scenes shared between
`SfM` and `MVRecon`. **Scene type:** mixed -- `Ignatius`/`Truck` are
outdoor object-centric captures (verified against a real sample image:
`Ignatius` is an outdoor campus statue); `Barn`/`Caterpillar` are outdoor
structures/vehicles; `Courthouse`/`Meetingroom` are large indoor/building
interiors. All static, real (handheld/rig video capture). **License:**
restricted_noncommercial -- CC BY 4.0 for citation, plus the benchmark's
own license page restricts installation/use to non-commercial scientific
research.

### SfM / imc

Image Matching Challenge (IMW2020) Phototourism TestData
(`cs.ubc.ca/research/image-matching-challenge/`), sourced from
Flickr/YFCC100M community landmark photo collections. 8 scenes
(`british_museum`, `florence_cathedral_side`, `lincoln_memorial_statue`,
`milan_cathedral`, `mount_rushmore`, `piazza_san_marco`,
`sagrada_familia`, `st_pauls_cathedral`). **Scene type:** outdoor
landmark/tourist photography, static, real (unstructured community
photos, not a rig capture). **License:** unconfirmed -- mixed per-image
licenses inherited from the source Flickr photos; check the `LICENSE.txt`
in each scene folder rather than assuming a single blanket license.

### MVRecon+SfM+SLAM / 7scenes

Microsoft 7-Scenes (Shotton et al., CVPR 2013). 7 scenes (`chess`,
`fire`, `heads`, `office`, `pumpkin`, `redkitchen`, `stairs`) for MVRecon.
SLAM uses the 18 official `TestSplit.txt` sequences, one case each:
`scripts/preprocess/materialize_7scenes_slam.py` builds
`SLAM/7scenes/<scene>_seq-NN` from relative symlinks into `MVRecon/7scenes`
(17,000 frames, no duplicated data; each case is one continuous recording with
its own small `sparse/0`). MVRecon keeps using the whole scenes: it scores fused
geometry against the GT mesh, a different measurement from SLAM's trajectories. 7-Scenes was removed from the SfM track on
2026-10-06: it duplicated the old SLAM track exactly.
**Scene type:** indoor (single rooms), static scene content with a moving
handheld camera, real (Kinect RGB-D). **License:** restricted_noncommercial
-- Microsoft Research License Agreement, non-commercial use only.

### MVRecon+SfM / dtu

DTU MVS / Robot Image Data Sets (Aanæs et al., IJCV 2016). 15 scans
shared between `MVRecon` and `SfM`. **Scene type:** object-centric
(tabletop objects/figurines under a robot-arm-mounted camera rig, studio
lighting), static, real. **License:** unconfirmed -- no formal license
document published by the source; the site describes the data as
"freely available" for research, with citation requested.

### MVRecon+SfM / scannetpp

ScanNet++ (Yeshwanth et al., ICCV 2023), materialized via
`depth-anything/DA3-BENCH`'s 20-scene evaluation package. 20 scenes
shared between `MVRecon` and `SfM`, by far the largest per-scene image
counts in this benchmark (up to 15,320 canonical images in one scene,
capped to 100 evaluated). **Scene type:** indoor (high-fidelity laser +
DSLR scans of real rooms/apartments/offices), static, real. **License:**
restricted_noncommercial -- ScanNet++ Terms of Use, non-commercial
research/educational use only, **no redistribution without TUM's written
permission** beyond holding your own signed data-use agreement.
**Data-leakage note:** excluded from the aggregate ranking/leaderboard
score (kept in the registry and per-dataset tables) -- see
`docs/benchmark/data_leakage_notes.md`; most benchmarked methods disclose
training on this exact dataset.

### MVRecon+SfM / hiroom

HiRoom, Depth Anything 3's own original synthetic (Blender-rendered)
indoor-room benchmark, released as part of `depth-anything/DA3-BENCH`. 30
scenes shared between `MVRecon` and `SfM`. **Scene type:** indoor (living
rooms/kitchens, professionally art-directed), static, synthetic (verified
against a real sample image: photorealistic rendered interior).
**License:** restricted_noncommercial -- DA3-BENCH's HF license tag is
"other"; the card states research/evaluation use only and asks users to
obtain proper permissions before other use. Never used as *training* data
by DA3 or (as far as researched) anyone else, so it carries no data-leakage
risk regardless of which method is being evaluated on it.

### SfM / texturepoorsfm

TexturePoorSfM from DetectorFreeSfM (He et al., CVPR 2024), fetched by
`scripts/download/texturepoorsfm.sh` from the Google Drive archive linked in
DetectorFreeSfM's `DATASET_PREPARE.md`. The raw data is 1,020 "bags" over 17
objects (`{object}__{5|10|20}bag{NNN}`); bags of one object are re-samplings of
one capture and share byte-identical frames and poses (818 unique frames in
total). **Split v2 (2026-09-24):** the benchmark uses 30 bags (350 images, 2 bags
of each size per object) from the held-out objects 1000, 1003, 1014, 1027, 1030
only, as listed in `scripts/preprocess/assets/texturepoorsfm_split_v2.json`. The
other 12 objects are the TexturePoorSfM training set. The v1 benchmark (30 bags
covering all 17 objects, whose frames also appeared in the training pool) was
removed on 2026-09-24; v1 results are not comparable with v2. **v1 GT poses are inverted:** the raw pose files are
world-to-camera (DetectorFreeSfM's evaluator reads them as such), but the old
`materialize_texturepoorsfm.py` inverted them, so every v1 model (and the
old `texturepoorsfm_train` bags) stored camera-to-world matrices as COLMAP
world-to-camera poses. LoFTR matches agree with the uninverted poses (median 75%
of matches within 4 px Sampson error vs 0% for the stored poses on object 1003).
Relative-rotation angles are unaffected by the inversion, but camera centers,
translation directions, ATE and AUC were scored against wrong GT, so all v1
texturepoorsfm pose results must be re-run on v2, whose poses are corrected by
`consolidate_texturepoorsfm.py --source_pose_convention inverted_w2c`. **Scene type:** object-centric (tabletop, deliberately
low-texture household objects), static, real. **License:** unconfirmed -- the
authors state no data license; do not include in a public release (already
excluded by default from `scripts/release/pack_and_upload_benchmark_datasets.py`).

### MVRecon / nrgbd

Neural RGB-D Surface Reconstruction dataset (Azinović et al., CVPR 2022,
`github.com/dazinovic/neural-rgbd-surface-reconstruction`). 9 scenes
(breakfast_room, complete_kitchen, green_room, grey_white_room, kitchen,
morning_apartment, staircase, thin_geometry, whiteroom), 10,970 images
total. Poses are published as OpenGL-convention camera-to-world matrices;
`scripts/preprocess/materialize_nrgbd.py` converts them to COLMAP
world-to-camera before writing `sparse/0` (verified against the dataset's
own `get_rays_np()` ray-direction convention in its official codebase, not
guessed). Depth uses `depth_filtered/` (the network-quality depth the
official codebase itself trains/evaluates on) at the official
`depth_shift=1000.0` (mm) scale. Ships with published `gt_mesh.ply` per
scene (from the same release's `meshes.zip`) for MVRecon
accuracy/completion/precision/recall/fscore. **Scene type:** indoor
(dining rooms, kitchens, a staircase, an apartment), static, synthetic
(Blender-rendered -- verified against a real sample image: a photorealistic
rendered dining table with marble top and a pitcher/teacups). **License:**
permissive but **per-scene, not uniform** -- each of the 9 scenes is
individually CC-BY or CC-0 depending on which BlendSwap artist it came
from; check the repo's own table before redistributing any single scene.

### SLAM / tum_dynamics

TUM RGB-D SLAM Dataset (Sturm et al., IROS 2012,
`cvg.cit.tum.de/data/datasets/rgbd-dataset`), "Dynamic Objects" category.
9 sequences (1 freiburg2: `desk_with_person`; 8 freiburg3:
`sitting_{static,xyz,halfsphere,rpy}` and
`walking_{static,xyz,halfsphere,rpy}`), 10,806 images total after
timestamp association (`scripts/preprocess/materialize_tum_dynamics.py`
implements the dataset's own standard greedy nearest-neighbor
rgb/depth/groundtruth association, `max_difference=0.02s`). Camera
intrinsics are the dataset's own official per-camera calibration:
freiburg2 has real lens distortion (COLMAP `FULL_OPENCV` model, 12
params including `k3`) while freiburg3 images are pre-undistorted
(`PINHOLE`). Depth PNGs are copied through at the dataset's native
16-bit/5000 scale, declared as `depth_png_scale: 5000` in the dataset's
`metadata.json` so `rgb_depth` depth priors are converted to metres correctly
(`adapter_utils.load_depth_priors`; without it the loader's millimetre default
would make them 5x too large) (SLAM evaluation is pose-only -- ATE/RPE/drift, see
`docs/benchmark/slam_protocol.md` -- so no per-dataset `gt_depth_scale` entry was needed in
`depth_prediction_evaluator.py`, unlike the MVRecon/VideoDepth datasets).
**Scene type:** indoor (an office setting), dynamic (people sitting/moving
in front of and walking through the camera's view -- verified against a
real sample image), real (Kinect RGB-D). **License:** permissive -- data
is CC BY 4.0; the accompanying toolkit code (not used here) is
BSD-2-Clause.

### SLAM / oxford_spires

The Oxford Spires Dataset (Tao et al., IJRR 2026,
`dynamic.robots.ox.ac.uk/datasets/oxford-spires/`): 10 handheld sequences
around Oxford colleges, libraries and the observatory quarter
(`bodleian-library-02`, `christ-church-{02,03,05}`,
`keble-college-{02,03,04,05}`, `observatory-quarter-{01,02}`), 38,380 images.
`scripts/download/oxford_spires.sh` fetches only what the pose evaluation
needs (each sequence's raw images, its ground-truth trajectory and the
calibration, ~76 GB); `scripts/preprocess/materialize_oxford_spires.py` runs
LingBot-Map's own preprocessing (fisheye cam0 rectified, the first 3,840
frames per sequence, each matched to the ground-truth pose within 0.1 s)
into `SLAM_source/oxford_spires`.
1440x1080 after rectification, fed at 504x378. Short range at stride 12
(LingBot-Map's `oxford.yaml`), large range at every frame. No depth, so
`rgb` only. **Scene type:** outdoor, campus-scale, real, with loops.
**License:** CC BY-NC-SA 4.0.

### SLAM / vbr

VBR: A Vision Benchmark in Rome (Brizi et al., ICRA 2024,
`rvp-group.net/slam-dataset.html`), in LoGeR's processed release (HF
`Junyi42/vbr_processed`, `scripts/download/vbr.sh`), which LoGeR and
LingBot-Map evaluate on: the 7 training sequences with public ground truth
(`campus_train{0,1}`, `ciampino_train1`, `colosseo_train0`, `diag_train0`,
`pincio_train0`, `spagna_train0`), 86,678 images, one camera frame per 10 Hz
LiDAR sweep. The ground-truth row k belongs to the k-th sorted frame, not the
frame with file number k (`scripts/preprocess/materialize_vbr.py`). 1388x700,
center-cropped to 2:1 and fed at 504x252; large range only. No depth, so
`rgb` only. **Scene type:** outdoor, city-scale, real (handheld and car).
**License:** unconfirmed -- no data license stated (site: (c) RVP-Group);
evaluated only, never redistributed.

### SLAM / kitti_odometry

KITTI Odometry (Geiger et al., CVPR 2012,
`cvlibs.net/datasets/kitti/eval_odometry.php`), as LoGeR, LingBot-Map and
VGGT-Long evaluate it: the left color camera (`image_2`) of sequences 00-10,
the ones with public ground truth, 23,201 images at 10 Hz
(`scripts/download/kitti_odometry.sh`). The ground truth is cam0's (left
grayscale) trajectory; `scripts/preprocess/materialize_kitti_odometry.py`
moves it to cam2, which is rectified to the same orientation about 6 cm to
the left, through the calibration's `P2 = K2 [I | t]`. 1241x376 (00-02),
1242x375 (03) and 1226x370 (04-10), center-cropped to 504:154 and fed at
504x154; large range only. No depth, so `rgb` only. **Scene type:** outdoor,
driving (urban, residential, highway), real. **License:** CC BY-NC-SA 3.0.

MVRecon.

directory; see `copy_path()` in `scripts/preprocess/materialize_da3_bench.py`,
`copy_entry()` in `scripts/preprocess/normalize_benchmark_layout.py`, and
`copy_depths()` in `scripts/preprocess/finalize_mvrecon_layout.sh`.

duplicate-free: `SfM/eth3d`, `SfM/tanks_and_temples`, `3DGS/dtu` and `3DGS/tanks_and_temples` link to their `MVRecon/` folders, and

(`scripts/preprocess/materialize_7scenes_slam.py`); the release archives keep these relative links.

`MVRecon/eth3d/<scene>/dslr_calibration_undistorted/` is the ground-truth
camera-pose source for MVRecon ETH3D. The adapter prefers that COLMAP model
when a scene does not provide `sparse/0`.

`gt_mesh.ply` and `gt_pointcloud.ply` are DA3-BENCH's published, pre-fused
ground truth (TSDF-fused RGB-D once at dataset-build time, not computed
per evaluation run -- see `depth-anything/DA3-BENCH` on Hugging Face and
`depth_anything_3/bench/datasets/{sevenscenes,eth3d,scannetpp}.py`).
`mvrecon_evaluator.py::resolve_gt_geometry_path()` reads whichever of
`gt_point_path`/`gt_pcd_path`/`gt_mesh_path`/`dense_gt_path` a scene's
`metadata.json` entry sets; DTU and Tanks-and-Temples do not set any of
these and keep their own dedicated evaluators instead (see
[MVRecon Metrics](#mvrecon-metrics)). A scene with none of these set and no
evaluator-specific fallback fails MVRecon evaluation with "No GT point
cloud or mesh registered" -- currently `eth3d/meadow` and `eth3d/terrace`.

DA3-BENCH's ScanNet++ and HiRoom subsets are materialized into the canonical layout with:

```bash

python scripts/preprocess/materialize_da3_bench.py \
    --source_root $SPATIALARENA_ROOT/da3_bench \
    --benchmark_root $SPATIALARENA_ROOT/benchmarks \
    --datasets scannetpp hiroom
```

## Methods and Tracks

This benchmark suite separates **method identity** from **input modality track**.
The evaluator still consumes standardized prediction artifacts only:

- `depths/<stem>.npz` for depth metrics: one float32 map per frame, compressed (`np.savez_compressed`, array
  `depth`), with the method's own confidence in `confidences/<stem>.npz` (float16, array `confidence`) and, for
  disparity / log-depth models, the unconverted output in `raw_disparities/` / `raw_log_depths/` (same format). Every
  adapter writes them through `adapter_utils.save_prediction_map`. Predictions exported before 2026-11-17 are `.npy`
  (float32 depth, float16 confidence) and are still read.
- `sparse/0/{cameras,images,points3D}.{bin,txt}` for pose/SfM metrics
- optional `points3D_dense.ply` for artifact visualization

(`scripts/inference/iggt4d.py`); the instance head is skipped.
`DEPTHLM` and `QWEN3_VL` use a point-query depth adapter: their upstream APIs
return scalar text depth answers for queried pixels, so the adapter queries a
fixed grid and interpolates those scalar answers into dense `depths/<stem>.npz`
benchmark artifacts. DepthLM requires gated Hugging Face access via
`DEPTHLM_CKPT_PATH`; the default `facebook/DepthLM` currently returns a gated
403 for this account.

The commercial VLMs (`CLAUDE_OPUS_5_5` = `anthropic/claude-opus-5.5`, `GPT_6_ASTRA` = `openai/gpt-6-astra`,
`GEMINI_4_ARGON` = `google/gemini-4-argon`) are queried through OpenRouter by
`scripts/inference/openrouter_vlm_depth.py`, on MonoDepth only. Each image is sent
once (long side 1024 px) as two images, the clean photo and a copy with a 16x16 grid of numbered red markers, and the
model returns every marker's metric depth as one JSON object (prompt `grid-v2`; a marker on the sky may be answered
`"sky"`). The 256 samples become a dense map by bilinear interpolation of the grid; a missing cell (`"sky"` or an
unparsed answer) takes the mean log depth of its answered neighbours instead of a single scene median, which would
leave a flat block per gap. One call per image instead of one per point keeps the cost to about 11,650 calls per
model for the full MonoDepth suite. The protocol was chosen on a 14-image pilot (2 per dataset): the `grid-v2`
prompt lowered aligned AbsRel by about 9% over the original 8x8 `grid-v1` prompt, 16x16 lowered it a little more, and
neither an RGB-guided joint bilateral fill (`OPENROUTER_DEPTH_INTERPOLATION=joint_bilateral`), a second refinement
call around depth edges (`OPENROUTER_REFINE_POINTS`), nor a task-framing system prompt (`OPENROUTER_SYSTEM_PROMPT=
depth-expert`) improved the aligned scores; those options remain available but are off. An answer that stops partway (some models occasionally answer only the first rows of dots and say so) gets
up to two completion follow-ups in the same conversation, asking for exactly the dots it left out (not those
answered `"sky"`); the follow-up answers fill those dots, and the rounds stop early when a follow-up adds
nothing. This is a request for the rest of the answer, not a re-sample, and applies to every model
(`OPENROUTER_COMPLETION_FOLLOWUPS`, default 2; `metrics.json` records `followup_calls` and
`followup_filled_points`). The engine's prediction cache
key includes these `OPENROUTER_*` settings for the OpenRouter methods, so changing them never reuses old maps. Requests use temperature 0, reasoning effort `low`
(`OPENROUTER_REASONING_EFFORT`) and `provider.data_collection: deny` (providers that may store or train on prompts
are not used; `OPENROUTER_ALLOW_DATA_COLLECTION=1` lifts this). The key comes from `OPENROUTER_API_KEY` or
`OPENROUTER_API_KEY_FILE`; without one the run is reported as `credentials_missing`. Parsed answers are cached
under `OPENROUTER_CACHE_DIR` (keyed by model, prompt version, settings and image bytes), so a rerun pays only for
images not yet answered, and `OPENROUTER_MAX_COST_USD` stops an adapter invocation once its billed cost reaches the
cap. `metrics.json` records the calls, cache hits, tokens and USD cost, and `openrouter_outputs.jsonl` keeps each raw
answer. A frame with no parseable answer gets the scene's median depth and is counted in `fallback_imputations`.
Before interpolation each sampled depth is clamped to the scene's `metadata.json` `[min_depth, max_depth]` (no
bound where the scene declares none), so out-of-range answers such as sky points thousands of metres away do not
bleed into neighbouring pixels; the evaluator's own post-alignment clip cannot undo that. `metrics.json` records the
range and `clamped_points`; `OPENROUTER_DEPTH_CLAMP=0` turns it off.
`configs/benchmark/api_vlm_monodepth.yaml` runs all five locally (`job_system: native`).
OpenRouter reports only running totals per key, so FeedForward-Benchmark's `scripts/inference/openrouter_usage.py poll` records them
(all-time, today, week, month; USD) to `~/.local/state/feedforward_benchmark/openrouter_usage.jsonl`, and
`openrouter_usage.py report --hours 48` lists the samples with the spend between them in London time. Polled every 30 minutes
from cron, this shows when the key was used outside a benchmark run; the per-request detail is on OpenRouter's
Activity page.
FeedForward-Benchmark's `app/openrouter_usage/server.py 8030` serves a page that charts these samples (see its README).

Single-pass input limits on one H200 (measured 2026-10-06 with
`scripts/test/profile_max_input_frames.sh` at 640x480; full table in
`docs/benchmark/slam_protocol.md`): `DUST3R` and `POW3R` cannot run the
100-frame full-standard cap -- their complete-graph global alignment (9,900
pairs at 100 frames) exceeds the 180 GB host-RAM limit of a GPU job -- and
`GENCEPTION_POSE` always resamples its input to 81 frames, so on cases with
more than 81 frames it returns 81 poses. In the SLAM track these budgets decide
which range tracks a method is in (`spatialarena/slam_protocol.py`). MapAnything,
MASt3R, Déjà View, DUSt3R and Pow3R, whose budgets are below even the short range's
longest input (364 frames), and IGGT4D (not measured) are attempted on the short and
long ranges, each failed sequence recorded with its cause, but not on the large range,
where they run out of memory; only GenCeption-Pose is not evaluated on SLAM.

`VGGT_LONG`, `PI_LONG` and `VGGT_SLAM` are long-sequence SLAM systems
(github.com/DengKaiCQ/VGGT-Long, github.com/DengKaiCQ/Pi-Long,
github.com/MIT-SPARK/VGGT-SLAM). They chunk a recording internally (overlapping
chunks or SL(4) submaps, aligned and loop-closed with SALAD retrieval), so they
have no frame budget, and they take part in the SLAM track only

### Input-resolution and confidence policy

Each canonical method has a default input profile in
`scripts/test/benchmark_methods.py`. `run_method_case_list.sh` applies that
profile to both depth and pose suites unless `RESOLUTION`,
`IMAGE_LOAD_RESOLUTION`, `PIXEL_LIMIT`, `CONF_THRESH`, or
`DEPTH_CONF_THRESH` are explicitly set in the environment.

Canonical full-standard profiles:

- `DA3-L`, `DA3-G`, `DA3-NGL`: `504`
- `VGGT`, `FASTVGGT`, `MAPANYTHING`, `OMNIVGGT`, `ROBUSTVGGT`: `518`
- `PI3_X`: `512`, with `PIXEL_LIMIT=262144`. RGB-only Pi3 runs use
  Pi3's official evaluation preprocessing: resize image width to `512`,
  preserve aspect ratio, then interpolate both axes to a multiple of the
  14-pixel patch size. This is shared by depth and pose runs. Pi3X multimodal
  tracks use the upstream multimodal loader, which accepts the same pixel-limit
  profile for RGB+depth/RGB+cameras priors.
- `CUT3R`, `FAST3R`, `VGGT_OMEGA`, `POW3R`, `DUST3R`, `MAST3R`: `512`
- `COME`, `DEJAVIEW`, `IGGT`, `IGGT4D`: `504`
- VLM depth adapters, including point-query adapters: `224`

The profile is recorded in `<REPORT_DIR>/summary.json` as
`resolution_profile`. Dense depth metrics ignore model confidence maps and use
canonical GT/depth masks only, matching the Pi3 depth evaluation convention of
filtering by ground-truth validity rather than prediction confidence.
`CONF_THRESH` and `DEPTH_CONF_THRESH` affect point-cloud/COLMAP export, not
dense-depth metric pixel selection. If a confidence-thresholded result is
needed later, report it as a separate coverage-aware track rather than mixing it
with the canonical dense-depth ranking.

Depth and pose runs share the same default profile for a method/track unless `RESOLUTION`,
`IMAGE_LOAD_RESOLUTION` or `PIXEL_LIMIT` are overridden (this replaced an older non-canonical setup where
full-depth defaulted to `518` and full-pose to `224`). MVRecon can be run at `518` as an explicit override when
reproducing Pi3's own MVRecon setting. The `resolution_profile` block in `summary.json` records the resolved input
size, image-load size, pixel limit, point-cloud and dense-depth confidence thresholds, and a provenance note.

Override example:

```bash
sbatch --export=NIL,RESOLUTION=518,IMAGE_LOAD_RESOLUTION=518,PIXEL_LIMIT=268324 \
  spatialarena/templates/_engine/run_method_benchmark_infer.sh PI3_X full-depth
```

## Protocol

This matrix mirrors `depth_prediction_evaluator.py::resolve_depth_config` (the default `standard` protocol), `mvrecon_evaluator.py::protocol_for_dataset`, and the case lists `scripts/test/full_standard_{depth,sfm}_cases.txt`. Development smoke tests may subsample further; those sampled runs are not the benchmark protocol.

### Frame Selection

Every `full-depth` and `full-pose` case is capped at `BENCHMARK_MAX_INPUT_FRAMES=100` (set by `run_method_case_list.sh` for both suites, matching DA3-BENCH's `max_frames: 100`). Scenes with more than 100 images use a fixed-seed (`42`) random subset that is re-sorted into canonical order (`scripts/inference/adapter_utils.py::resolve_capped_image_indices`). All `full-depth`/`full-pose` case lists use `interval=1`. A dataset can set its own cap (`DatasetSpec.max_input_frames` in `spatialarena/eval/dataset_registry.py`, applied per case to both `BENCHMARK_MAX_INPUT_FRAMES` and `MAX_IMAGES_PER_RUN`): SpatialArena's VideoDepth clips (132-1,021 frames) are fed and scored whole, and its MVRecon and SfM scenes are capped at 300 images. The whole subset goes through one forward pass, so a scene's predictions share one coordinate frame. MonoDepth is not capped (every image is scored; see below). SLAM (`full-slam`) is the other exception: each case is a whole recording at its range track's stride with no cap and no subsampling, and a method only runs the tracks whose longest sequence fits its H200 single-pass budget (`docs/benchmark/slam_protocol.md`).

**MonoDepth is single-view.** For a MonoDepth case the engine exports `BENCHMARK_SINGLE_VIEW=1`
(`run_method_case_list.sh`), and every image is predicted on its own, never as one view of a multi-view batch
of the case's frames. DA3, VGGT, RobustVGGT, Pi3 and IGGT run the frames as independent single-view samples, a
`[B, 1, 3, H, W]` batch whose outputs are folded back to the sequence layout
(`adapter_utils.fold_single_view_outputs`); the nested DA3 (DA3-NGL), which fits one depth scale and one sky depth
over its whole input, and every other multi-view method run one image per forward pass
(`adapter_utils.batched_image_paths` returns one-image chunks; Fast3R, OmniVGGT and Deja View use their own
loops); the pairwise DUSt3R / MASt3R / Pow3R run the image as the pair (image, image), DUSt3R's monocular mode;
the VLM point-query methods already answer per image. MonoDepth has no frame cap: every image of a scene is
predicted and scored (`adapter_utils.resolve_capped_image_indices` skips `BENCHMARK_MAX_INPUT_FRAMES` and
`MAX_IMAGES_PER_RUN` in single-view mode). A scene with more than `MAX_IMAGES_PER_RUN` (100) frames, or whose frames
differ in size (AerialMetric mixes cameras), runs the adapter once per image size and per 100 frames
(`BENCHMARK_IMAGE_SUBSET`, `scripts/inference/single_view_groups.py`) and merges the per-frame outputs, so no
adapter loads more than 100 frames at once, a frame is never resized to fit, or stacked with, a frame of another
size, and its prediction does not depend on which frames shared its batch. A MonoDepth prediction is reused only if
it covers every frame of the scene, so predictions made under the former 100-frame cap (results before
2026-10-20) are re-run. Single-view predictions have their own prediction-cache key,
so earlier multi-view MonoDepth predictions are never reused. Results produced before 2026-10-16 fed up to 100
frames of a case to multi-view models in one pass and are superseded.

## Metrics

Dataset-level summaries follow the benchmark metric unit: MonoDepth averages images, VideoDepth averages
sequences, ATE weights by matched images, and relative pose metrics weight by image pairs. The SLAM track's
metrics (ATE, RPE, drift, pose AUC, completeness) and ranking are defined in
[`benchmark/slam_protocol.md`](benchmark/slam_protocol.md).

### Depth Metrics

Depth predictions are loaded from `depths/` (the GT-only inverse-depth protocols read `raw_disparities/` instead when a method exports it). Dense prediction maps are resized to the ground-truth depth shape, aligned according to the protocol, optionally clipped, and scored on valid ground-truth pixels. The `standard` protocol and the GT-only protocols resize bilinearly; the named Pi3 protocols use cubic resizing to match Pi3/CUT3R evaluation behavior. Validity masks are expected to be materialized at ground-truth resolution when available. Pairing first uses normalized filename keys. Bonn additionally falls back to nearest RGB-D timestamps within `0.25s`; Tanks-and-Temples depth rows fall back to integer-index pairing with a `+1` ground-truth offset.

Valid pixels satisfy `isfinite(gt)`, `isfinite(pred)`, `gt > min_depth`, and dataset `max_depth` when configured. The GT-only protocols select pixels from the ground truth alone (`isfinite(gt)` and the dataset range), so a non-finite prediction on a GT-valid pixel fails the case instead of being dropped. A non-positive native depth on a GT-valid pixel (no `raw_disparities/` exported) is floored to `1e-5` before the fit and scored there, rather than failing the scene; `floored_nonpositive_pixels` in the fit diagnostic records how many. This is intentionally a ground-truth-validity protocol: dense-depth metrics do not apply model confidence thresholds, matching the Pi3 evaluation code path and avoiding method-specific coverage changes. The evaluator does not require positive predictions before alignment unless `--require_positive_prediction` is explicitly set. Adapter confidence thresholds remain available for point-cloud/COLMAP artifact export only. If confidence-filtered depth metrics are added later, they must be reported as a separate coverage-aware track. Metric computation clamps `pred` and `gt` to at least `min_depth` to avoid division by zero.

Aggregation follows a fixed unit weighting:
- MonoDepth computes metrics per image and averages images uniformly.
- VideoDepth fits one alignment per sequence (by default the GT-only Huber IRLS fit in the method's native output space, see below), computes sequence-level metrics, then averages sequences uniformly.

The evaluator reports both depth-ratio threshold families:
- `Delta@1.03` is the stricter threshold.
- `Delta@1.25` follows the VGGT-Omega/common depth protocol. `Delta@1.25^2` and `Delta@1.25^3` are also reported.

Named depth protocols:
- `standard` resolves task/dataset-specific benchmark alignment, scale, clipping, and valid-depth ranges. For MonoDepth it is a per-image least-squares scale+shift fit in depth space (the eth3d fit on at most 1024 px); for VideoDepth, one Pi3/CUT3R scale+shift LAD fit per sequence with cubic resizing.
- `pi3_mono` uses Pi3/CUT3R scale-only robust alignment and cubic prediction-depth resizing for MonoDepth-style datasets.
- `pi3_video` uses Pi3/CUT3R scale+shift LAD2 alignment across the whole video sequence and cubic prediction-depth resizing for Sintel, Bonn, and KITTI.
- `custom` leaves the explicit CLI alignment, resize, scale, and clipping flags unchanged.
- GT-only protocols (ported from PR #21; `spatialarena/eval/inverse_l1_gt.py`, `depth_space_gt.py`, `huber_irls.py`). Each takes the `standard` dataset ranges and clipping, uses bilinear resizing, fits on every GT-valid pixel (no prediction-dependent exclusion), scores on the same pixels, writes its fit to `<protocol>_fit.json` (`<protocol>_fits/<image>.json` for MonoDepth), and reports the normal error `mae_normal_deg` (on each frame's full aligned depth map, averaged over frames; needs intrinsics, off with `--no_geometry_metrics`) but no point-cloud metrics. Each frame's aligned map (the fit, floor and clip behind its score) also goes to the per-frame writers, so `--error_artifact_dir` and the dashboard viewer assets (`--viewer_dir`) work as on the `standard` path:
  - `inverse_huber_irls_gt`: affine fit `a*q + b` of the prediction's inverse depth `q` (or its `raw_disparities/`) to GT inverse depth with a Huber loss (delta `0.05` on residuals divided by the GT median), solved by IRLS from the L2 solution; the aligned inverse depth is floored (`--inverse_floor_policy`: `fixed` = `1e-3`, `gt_max` = `1/max(GT)`, MonoDepth only) and inverted.
  - `inverse_l1_gt` / `inverse_l1_l2init_gt`: the same inverse-depth affine fit with an L1 loss solved by Adam, initialised from the median ratio or the L2 solution.
  - `depth_huber_irls_gt`: the Huber IRLS affine fit in depth space (native depth; non-positive depth floored to `1e-5`).
  - `gt_bounds_direct` / `gt_bounds_depth_huber_irls`: oracle diagnostics for normalized-disparity models: decode `raw_disparities/` with the sequence's GT inverse-depth 2%/98% quantiles (then optionally the depth-space Huber fit). They use GT to decode and are not comparable benchmark numbers.

The engine picks the protocol per task and method: `MONO_DEPTH_PROTOCOL` and `VIDEO_DEPTH_PROTOCOL`, set in a model's config `env:` block, take precedence; otherwise the protocol follows the method's registered `depth_output_space` (`spatialarena/methods.py`): `depth` selects `depth_huber_irls_gt` and `inverse_depth` (LOTUS_D, DVD, DEPTHCRAFTER) selects `inverse_huber_irls_gt`, so each prediction is aligned in its native output space (`docs/benchmark/depth_methods.md`). Unregistered methods keep `inverse_huber_irls_gt`. `MONO_INVERSE_FLOOR_POLICY` defaults to `gt_max`.

Source references:
- Pi3/CUT3R alignment behavior follows the Pi3 `evaluation` branch depth evaluation utilities at `https://github.com/yyfz/Pi3/tree/evaluation`.
- DA3-BENCH dataset/layout and fused reconstruction settings follow Depth-Anything-3 benchmark documentation and code at `https://github.com/ByteDance-Seed/Depth-Anything-3/blob/main/docs/BENCHMARK.md`.
- Depth-unprojected point accuracy, completion, and Chamfer metrics follow the local FoundationModels reference in `~/Projects/FoundationModels/fdms/evaluators/recon_evaluator.py`.

- No optional external-compatibility mode is part of the canonical evaluator.

### MVRecon Metrics

The MVRecon evaluator (`spatialarena/eval/mvrecon_evaluator.py`) consumes
canonical `depths/` and `sparse/0` artifacts and runs in `unposed` mode by
default (`--reconstruction_protocol unposed`; the full-standard runner does not
override it). In `unposed` mode it:

1. aligns the predicted poses to GT with the pose-aware Sim(3) estimator
   (`pose_alignment.py::ransac_irls_align_sim3`, see Sparse Pose Metrics),
2. scales predicted depths by the recovered Sim(3) scale and masks them with
   the GT depth/validity mask,
3. fuses all views into an Open3D TSDF volume with the aligned predicted poses
   and predicted intrinsics, extracts a mesh, and samples `1,000,000` points,
4. crops ScanNet++ predictions to the GT bounding box. Tanks and Temples GT
   cameras live in the COLMAP frame but its laser scan does not: the evaluator
   maps the fused points and both camera sets into the laser frame with the
   official `<scene>_trans.txt` Sim(3), then crops prediction and GT with the
   official `<scene>.json` volume, as the Tanks and Temples toolbox does
   (`tanks_and_temples_registration`; the per-scene result records
   `gt_registration` and `crop_kept_fraction`). Only for datasets whose
   protocol enables it (`tanks_and_temples`, `dtu`, `nrgbd`) it then refines
   the fused points against GT with scaled ICP
   (`refine_fused_points_in_gt_frame`). The fused points are already in the GT
   frame (step 1, plus the registration above for Tanks and Temples), so ICP
   starts from the identity, and it pairs points only
   within `2 x` the dataset threshold, so background the GT does not cover
   cannot pull the fit. DTU's ICP target is the official laser scan
   (`Points/stl/stlNNN_total.ply`, moved into the scene frame and
   voxel-downsampled), not the sparse COLMAP `points.ply`; DTU fusion also
   masks each view with its image's alpha channel (the object mask, aligned
   with the cropped images),
5. measures the fused point cloud against GT geometry.

`7scenes`, `eth3d`, `hiroom`, and `scannetpp` use DA3-BENCH preprocessing and
run **no** dense ICP. In `posed` mode the same pipeline fuses with GT camera
poses and intrinsics, still applying the Sim(3) depth scale.

The fused reconstruction metrics follow Depth-Anything-3's public DA3-BENCH
code path in `bench/utils.py` and dataset wrappers under `bench/datasets/`.
For non-DTU datasets, `accuracy` is the mean nearest-neighbor distance from
predicted points to GT points, `completion` is the reverse direction,
`overall=(accuracy+completion)/2`, and `precision`, `recall`, and `fscore`
are computed at the dataset threshold. DTU uses the MVSNet-style ObsMask/Plane
filtering implemented in `spatialarena/eval/eval_dtu_mesh.py` and reports

### MVRecon scoring: memory bounds, invalid geometry, SpatialArena backprojection

The default reconstruction backend remains TSDF. Exact nearest-neighbor
queries now run in chunks, accumulating distance sums and match counts rather
than keeping every distance array. Thresholds, voxel downsampling, and metric
definitions are unchanged (floating-point summation order can differ).

Set these optional values in the model's `env` mapping of a standard YAML:

```yaml
env:
  MVRECON_METRIC_WORKERS: '1'
  MVRECON_METRIC_CHUNK_POINTS: '262144'
  FFB_SCORE_MEMORY_TRACE: '1'
```

Workers and chunk sizes must be positive. Memory tracing is off by default.
When enabled, JSON log lines identify input preparation, TSDF integration,
mesh extraction, GT loading, and nearest-neighbor batches, with process peak
RSS in KiB on Linux. This is a cumulative CPU-memory high-water mark, not GPU
memory or the instantaneous allocation of each stage. Chunking bounds query
batch memory; it does not bound the point clouds, KD-tree or TSDF volume.
These chunk controls apply to the generic MVRecon nearest-neighbor scorer;
DTU's official MVSNet scorer retains its own neighbor calculation.

#### Invalid DTU geometry

Empty or malformed fused/reference geometry and nonfinite coordinates fail
before scoring or writing a successful reconstruction. DTU also checks input
prediction, bounding-box mask, observation mask, reference STL, and reference
plane-mask point sets. Empty truncated-distance sets raise an explicit error
instead of returning NaN. The nonempty DTU metric computation is unchanged.
An empty reconstruction remains a failed case; it must not disappear from the
reported expected coverage.

#### SpatialArena direct backprojection (optional)

The MVRecon registry and canonical list include the six SpatialArena cases.
Their metadata and assets are under `<benchmark_root>/MVRecon/spatialarena`.
Each scene's `eval_threshold` (0.05 m indoors by default, 0.25 m outdoors)
scales the voxel and downsampling sizes, and the depth predicted views are
fused up to: 20 m indoors, 100 m outdoors, with per-scene exceptions in
`SPATIALARENA_FUSION_OVERRIDES` (`protocol_for_dataset` in
`spatialarena/eval/mvrecon_evaluator.py`). Backprojection uses the same
maximum depth and downsampling size.

To opt in, set `SPATIALARENA_MVRECON_BACKEND: direct_backprojection` in the
YAML model environment. This setting only affects SpatialArena; DTU and all
other datasets continue using TSDF. Direct backprojection uses aligned
camera-Z depths, intrinsics and world-to-camera poses, and retains the first
valid point per voxel in view/pixel order. It skips TSDF surface fusion and
mesh sampling, so it is a **different reconstruction protocol**, not an
equivalent memory optimization.

Reports record `reconstruction_backend`, voxel representative policy, and
`mesh_sampling: false`; TSDF-only parameters are null for backprojection.
Use a separate `benchmark_eval_root` and experiment name for this protocol.
For complete cached predictions, set `evaluate_only: true`, point
`FULL_ARTIFACT_ROOT` at the existing prediction root, and use the standard
`run_config <yaml> coverage`, review, then `submit` workflow. Do not overwrite
or aggregate TSDF reports with backprojection scores. These code changes do
not submit jobs or modify historical artifacts.

### Sparse Pose Metrics

Sparse pose evaluation (`spatialarena/eval/sparse_reconstruction_evaluator.py`)
serves `SfM` (the SLAM track has its own trajectory evaluator, see
`benchmark/slam_protocol.md`). It reads COLMAP `images.bin` or `images.txt` from
canonical `sparse/0` outputs and from canonical sparse ground truth. Images are
matched by filename. Relative pose metrics use all matched image pairs;
`--max_pairs > 0` is only a development cap. Relative metrics are aggregated
with pair weights, ATE with matched-image weights.

ATE is computed after a **pose-aware** Sim(3) alignment
(`pose_alignment.py::ransac_irls_align_sim3`, "RANSAC + GTSAM + robust
refit"), not a center-only Umeyama fit, which is degenerate on near-collinear
trajectories and not outlier-robust:

- each hypothesis is fitted with the cost of GTSAM's `TrajectoryAlignerSim3`
  (`fit_sim3_pose_residuals`: a rotation-geodesic plus a translation residual
  per camera, nonlinear least squares over rotation, translation and
  log-scale);
- RANSAC draws 2-camera minimal samples (25 iterations, seed 42) and selects
  the hypothesis with the least median squared center residual (LMedS);
- the inliers within `2.5 * sigma`, where
  `sigma = 1.4826 * (1 + 5 / (n - 2)) * sqrt(median r^2)`, are refit;
- that estimate is refined on *all* cameras by a Cauchy-weighted IRLS of the
  same cost (`irls_refine_sim3`). Rotation and translation residuals are each
  normalized by a robust scale (1.4826 x MAD), re-estimated every iteration,
  and the refit stops when the parameters stop moving. It makes the result
  independent of the RANSAC seed, while cameras with gross errors keep a
  near-zero weight.

The same estimator aligns poses for MVRecon fusion and for the SLAM track. A
3,450-trial simulation against evo's Umeyama, the previous estimator
(DAGSfM fit + ICP on the inlier centers) and RANSAC without the refit is
documented in `benchmark/slam_protocol.md` ("Choice of estimator"). The
previous estimator, `ransac_icp_align_sim3`, is kept for comparison only;
its ICP on camera centers is a center-only fit again. Results computed before
2026-10-09 used it.

The current full-pose scope excludes RealEstate10K and standalone ScanNet. It
covers SfM on ETH3D, Tanks-and-Temples, IMC, DTU, ScanNet++, HiRoom, and
TexturePoorSfM (`scripts/test/full_standard_sfm_cases.txt`). SLAM (7Scenes test
sequences, TUM RGB-D dynamic sequences, Oxford Spires, VBR and KITTI Odometry) is
its own `full-slam` suite, one case list per range track
(`scripts/test/full_standard_slam_cases_{short,long,large}.txt`). ScanNet++ stays in per-dataset
tables but is excluded from the aggregate ranking (see
`benchmark/data_leakage_notes.md`).

`RRA` follows the standard rotation-threshold summary. Direct relative translation-direction error is retained as `relative_translation_error_deg_*`, where a reversed translation direction remains an error. `RTA` and `mAA@30` use the standard translation-axis convention, where opposite translation directions are treated as the same epipolar geometry.

## Outputs

### Prediction layout


Expected prediction layout:

```text
EXPERIMENT_ROOT/EXPERIMENT_NAME/TASK/DATASET/METHOD/SCENE/
    depths/
    sparse/0/
    points3D_dense.ply
```

Depth evaluators consume `depths/`. Sparse pose evaluators consume COLMAP `sparse/0`. MVRecon and VideoDepth
inference also exports the predicted cameras as a points-free `sparse/0` for every method whose adapter predicts
them (`depth_only_exports_poses` in the engine): MVRecon fuses with them, and a VideoDepth prediction keeps its
predicted trajectory with them. A cached MVRecon or VideoDepth
prediction without `sparse/0` is not reused by inference (its case runs again); an evaluation-only VideoDepth run
still scores it. Geometry evaluators consume dense point/mesh artifacts when that task has an implemented geometry protocol.



This is the contract for a full-standard run: the checked-in case lists and the runner must produce the paths
and file names described here.

Each full suite has exactly one report folder per method (`spatialarena/report_layout.py`). Reruns, retries
and fixes write into it: finished cases are reused, rerun cases overwrite their results in place, and a split run
names each part's summary after its case file (`summary_<case file>.tsv`). The engine exits with code 8 when a
run targets any other folder inside `reports/`, so results never scatter across per-run folders.

The listed artifact files are conditional on the task:

- Depth tasks write `depths/`; sparse tasks write `sparse/0/`.
- MVRecon writes `eval_mvrecon.json`.
- MonoDepth and VideoDepth write `eval_depth.json`.
- SfM writes `eval_sparse.json`; SLAM (`full-slam` suite) writes `eval_slam.json`.
- `viewer/` holds what the dashboard's comparison modes draw, written by the evaluator while it holds the aligned
  data (`spatialarena/eval/viewer_assets.py`; the engine passes `--viewer_dir`, disable with `VIEWER_ASSETS=0`):
  `trajectory.json` for SfM and SLAM (the GT and the prediction aligned exactly as the ATE); for MonoDepth and
  VideoDepth, `depth/` and `error/` WebP frames plus `frames.json` (aligned depth on the scene's GT color scale and
  the absolute relative error); for MVRecon, the fused cloud in the GT frame with its colors and per-point
  nearest-GT error (`points.f32`, `colors.u8`, `error.f32`, `cloud.json`). A failure to write them is recorded as
  `viewer_error` in the scene result and never fails the evaluation.
- `metrics.json` is written by every built-in adapter. Besides the legacy
  per-adapter `inference time` / `Peak GPU Memory`, it holds the standard
  `inference_seconds`, `model_load_seconds`, `peak_gpu_memory_mib` and
  `runtime_scope` (see [Reporting](#reporting)); the evaluators copy
  them into each scene's `runtime` entry in `eval_*.json`, so they survive
  prediction deletion.
- `points3D_dense.ply` and `metrics.json` are optional method artifacts;
  `--depth_only` methods (used for every MVRecon full-depth case) write
  `depths/` and `sparse/0/` but skip the dense point cloud -- MVRecon
  evaluation fuses depth with the exported poses itself and does not need
  the adapter to pre-build one (see `mvrecon_evaluator.py::
  prepare_fusion_inputs`).
- `depth_visualizations/` is optional and controlled by
  `KEEP_DEPTH_VISUALIZATIONS` (default `1`) -- written for every task,
  including SfM/SLAM, not only depth tasks.
- `artifacts/<Task>/<Dataset>/<Scene>/fused_points.ply` is written for every
  MVRecon case (`evaluate_case()` always passes `--output_path`, which
  defaults `--artifact_root` to `<report_dir>/artifacts` unless overridden)
  -- it is the evaluator's own fused prediction point cloud, useful for
  inspection, not something the method adapter produces.

The runner preserves predictions for full evaluation by default
(`KEEP_PREDICTIONS=1`). A successful empty `case_failures.tsv` contains only
its header.

### Reporting


Per-scene evaluator outputs retain the resolved protocol fields, including alignment mode, GT scale, prediction scale, min/max valid GT depth, and prediction clipping. Summary tables should report dataset-level weighted averages, not sampled smoke-test numbers. Sampled DA3/VGGT jobs are useful for implementation checks, but their metrics should stay in experiment reports or temporary summaries rather than this document.

Runtime is reported alongside, not ranked. Every adapter's `metrics.json` carries standard runtime keys written by `scripts/inference/adapter_utils.py`: adapters call `mark_model_loaded()` once the model is on the GPU, which starts the timer and resets the CUDA peak-memory counter, so `inference_seconds` and `peak_gpu_memory_mib` cover inference only (the resident weights are still counted in the peak) and `model_load_seconds` covers everything before it; `runtime_scope` is `after_model_load`, or `adapter_started_at` for an adapter that never calls it. The evaluators copy these into each scene result as `runtime` (`spatialarena/eval/prediction_artifacts.py::read_adapter_runtime`), and `scripts/test/summarize_benchmark_reports.py` adds a per-method/dataset runtime table (mean inference seconds, seconds per input image, mean and max peak GPU memory). Predictions written before this instrumentation only have each adapter's own `inference time` / `Peak GPU Memory`, whose scope differs per adapter; they are labelled `legacy` and must not be compared with `after_model_load` rows. COME and external-command adapters run the model in a child process, so their peak GPU memory is empty.
